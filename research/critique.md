# 研究对抗性复核

## 怀疑型使用者

最容易失信的地方是把菜单、官方文档或源码类名当作可执行证明。当前矩阵已经把十个主模块的源码事实标为 verified，把受 feature gate 控制的能力标为 partial，把 DeepSeek/Kimi 真实调用标为 blocked。正式培训仍需为每个主链补充隔离环境的操作前、操作中、结果、失败和恢复证据。

## 对抗性评审

来源数量和分类已过自动门槛，但八个开发者案例都来自 GitHub Issues，视角仍偏向故障报告。它们适合构造失败 fixture，不适合衡量典型成功率或用户满意度。下一批研究应在不降低一手性标准的前提下补充公开的生产实现复盘，并仍然把经验与官方规则分开。

另一个风险是官方页面为滚动文档。部分页面更新时间晚于目标 3.1.3，尤其 Prediction、Embed、Workspaces、环境变量和生产运行。当前来源条目已记录日期和差异说明，关键参数仍要回查固定提交。3.1.4 Release 列出的安全修复也不能反推 3.1.3 一定存在可利用漏洞。

## 实施工程师

研究建议已经被压缩为可执行合同：Start 输入 fixture、Flow State session 对照、变量覆盖矩阵、SSE 事件状态机、浏览器 canary、RAG 状态机、MCP allowlist 和副作用 ledger。缺口是隔离环境、中文 SHA 与 Provider 凭据尚未提供，因此实验结果不能生成。

## 结论

当前研究库适合作为正文、站点骨架和测试脚本的事实输入，但不满足正式发布证据。继续增加二手文章不会解除关键阻塞；下一阶段应优先完成同版本运行态复现和截图安全门禁。
