# 执行记录与调试

## 从症状到根因的标准流程

1. **固定一次失败**：记录时间、流程、Session、触发方式和用户可见症状。
2. **缩小筛选**：按状态、时间、流程和 Session 找到唯一执行。
3. **读执行树**：找到第一个异常节点，而不是最后一个报错节点。
4. **比对输入输出**：确认错误来自上游输入、节点配置、Provider、工具还是下游系统。
5. **检查耗时与费用**：识别重试、循环、慢检索和模型调用放大。
6. **形成假设并做最小复现**：每次只改变一个变量。
7. **验证修复和回归**：正常、失败与恢复路径都要重跑。

## 关键字段

- 状态：运行中、成功、失败、停止或等待人工等。
- 时间：创建、开始、结束与节点耗时。
- 流程和版本：确认执行对应的是哪次保存后的对象。
- Session：关联同一会话或 HITL 恢复。
- 输入输出：可能包含敏感数据，公开截图前必须脱敏。
- token、费用和延迟：用于成本与性能分析，不应由客户端估算替代服务端记录。

## HITL 恢复

恢复前确认原执行确实处于可恢复状态，操作者有权限，流程版本未发生不兼容变化。Proceed 和 Reject 必须写入明确理由。恢复后检查新节点是否从正确断点继续，而不是从 Start 重跑副作用。

## 分享与删除

分享执行记录可能暴露提示、输入、工具参数和内部返回值。公开前默认不分享；确需分享时采用脱敏副本和最短有效期。批量删除是高风险操作，先记录筛选条件、数量和保留策略，再二次确认。

## 调试检查点

- 找到的是第一处异常，不是只处理最终错误。
- 修复解释了证据，而不是碰巧让一次运行成功。
- 外部写入通过目标系统回执核实。
- 日志和截图不含秘密、真实个人数据、内部域名和资源 ID。
- 未在生产环境通过重复触发来“排查”副作用。

本章正式截图需要覆盖筛选、执行树、节点详情、HITL、分享和危险删除确认，待 G1 后采集。

## 目标

用同一套证据顺序把用户症状定位到第一个异常节点，并完成最小复现、修复、恢复和清理。

## 适用角色

新手查看结果，搭建者定位节点配置，开发者分析 API／流式事件，管理员处理分享、恢复和批量删除。

## 适用版本与功能状态

适用于 Flowise `3.1.3`、提交 `96f6ae46…` 的执行记录模块；状态标签和详情字段待同版本隔离培训环境逐项截图确认。

## 前置条件与风险

需要唯一失败时间窗、流程 ID、Session 和触发方式。执行详情可能含提示、个人数据、工具参数和秘密；恢复或删除会产生写入。

## 初始状态

先清空筛选并记录总量，不分享、不恢复、不删除；从用户症状建立一个只读调查编号。

## 操作步骤

固定失败 → 筛选唯一执行 → 展开执行树 → 找第一异常节点 → 比对输入输出 → 检查 token/费用/延迟 → 建立单一假设 → 最小复现 → 验证恢复。

## 逐步检查点

确认流程版本和 Session 正确；异常节点上游输入可解释；外部写入有目标回执；HITL 从原断点继续而非重跑 Start。

## 成功结果

根因、证据、修复和回归形成一条可重复链；成功、失败、恢复运行均可定位，未靠生产重复触发试错。

## 常见错误与诊断

找不到记录先核对时区和筛选；树尾报错不一定是根因；无 token 不等于未调用；分享失败先检查权限；HITL 恢复失败检查原状态和版本。

## 回退与清理

恢复操作失败时停止继续点击，保留原执行；撤销临时分享，删除仅限本实验的记录，并确认业务系统未留下重复写入。

## 安全提示

公开前生成脱敏副本；禁止把完整输入输出、Cookie、Token、内部 URL 或资源 ID 放入截图和工单。批量删除必须二次确认筛选和数量。

## 练习任务

对一个 Provider 超时 fixture 执行标准诊断，定位第一异常节点，应用有限重试并验证成功与费用没有放大。

## 验收清单

- [ ] 唯一执行、第一异常节点和根因已确认。
- [ ] 成功、失败、恢复路径有证据。
- [ ] 分享、HITL、删除和敏感信息边界已检查。
