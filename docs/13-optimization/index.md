# 优化建议与关键 Tips

本章的建议必须满足证据要求：官方文档或源码锚点、至少两个独立开发者案例、培训环境复现。未完成三角验证的内容标为“经验建议”，不包装成官方规则。

!!! warning "当前全部为发布阻断的研究建议"
    本页引用的相关 Claim 仍含 `partial`／`proposed` 与 `blocked`／`not-started` 状态。以下卡片仅用于设计隔离实验，不是已验证的官方规则；发布模式会拒绝这些状态，直到来源、两个独立案例和培训环境复现全部闭合。

## 实践卡片：先压缩问题，再增加节点

- **问题**：流程变复杂后难以定位失败。
- **推荐做法**：先写出唯一输入、唯一输出和最小验证，再按清晰职责拆节点。
- **不适用**：独立合规步骤不能为了少节点而合并。
- **成本与风险**：节点太细会增加状态映射与观测成本。
- **复现实验**：对相同任务比较单体提示与三阶段流程的错误定位时间。

## 实践卡片：提示词使用显式契约

写清角色、任务、允许信息、禁止事项、输出 Schema、无答案行为和示例。上下文只提供完成任务需要的信息；外部检索结果按不可信数据处理。

## 实践卡片：Tool 描述决定可用性

名称使用动词和业务对象，说明何时调用、何时不调用、参数和副作用。查询与写入工具分开；写入要求幂等和人工确认。

## 实践卡片：RAG 先评检索再评生成

先看正确 chunk 是否进入 Top K，再看模型怎样回答。metadata 用于版本、权限和来源过滤；chunk 与 overlap 通过固定测试集比较，不凭感觉调整。

## 性能与费用

- 固定基准问题，分别记录节点耗时、Provider 延迟、token 和总费用。
- 限制 Agent 步数、Iteration 项数、工具调用数和上下文长度。
- 对确定性、可安全复用且不含敏感数据的结果考虑缓存。
- 重试采用有上限退避；写入请求必须幂等。

## 可观察性

流程设计时就定义执行记录需要回答的问题：哪个输入、哪一版本、哪个节点先失败、调用了什么、耗时和费用多少、外部系统是否返回业务回执。

## 常见反模式

| 反模式 | 后果 | 修正 |
| --- | --- | --- |
| 把秘密写进节点或变量 | 导出、日志和截图泄露 | 使用 Credential 与秘密存储 |
| 用一个 Agent 解决所有逻辑 | 非确定性、费用和调试困难 | 确定性规则显式化 |
| 无上限循环或重试 | 费用放大、重复写入 | 设置步数、超时、预算和幂等 |
| 只凭一次成功上线 | 隐藏失败路径 | 测试空、错、限流、恢复 |
| RAG 只调 Prompt | 无法修复检索缺陷 | 分层评估载入、切分、检索、生成 |
| 复制模板后直接发布 | 凭据和依赖漂移 | 替换环境依赖并重新验证 |
